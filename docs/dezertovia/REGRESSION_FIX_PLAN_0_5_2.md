## 2. UI-01/02 — сначала согласовать чат и окна

### 2.1. Состояния и приоритеты

1. В GamePage собрать единый признак экрана, который временно подавляет чат:
   меню, голосование, больница/карточка пациента, разговор с батюшкой, уже
   существующие диалоги **и выбранная карточка `showPicked`/`showWatched`**.
   Одинаково для жителя, помощника и царя. Не добавлять независимые условия в CSS
   для каждого окна: одно вычисленное состояние, явные слои UI.
2. Открытая карточка объекта получает видимый заголовок, крестик, содержимое
   и кнопки. Чат/всплывающие сообщения не рисуются поверх и не перехватывают тапы.
   Счётчик непрочитанных продолжает обновляться.
3. Временное скрытие не записывать как пользовательский выбор `hidden` в localStorage.
   Не размонтировать ChatPanel ради скрытия: сохраняются черновик, история,
   позиция чтения, обработанные сообщения и уведомления.
4. Обычный переход «карта → карточка → карта» возвращает прежний compact/hidden.
   При принудительном выходе из fullscreen не открывать его обратно неожиданно:
   вернуть quarter, снять inert/фокусировку и предоставить управление карточке.
   Проверить, что эффекты и cleanup полноэкранного чата учитывают interrupted,
   а не только смену режима. Уведомления, пришедшие под окном, не вспыхивают пачкой
   устаревших тостов после его закрытия.

### 2.2. Геометрия, тема и нажатия

5. Hidden-режим: маленькая кнопка в углу, отдельные ограниченные тосты. Сам
   контейнер прозрачный и не создаёт полноширинную непрозрачную полосу.
   Пустая область не является целью pointer-events; сама кнопка/тосты нажимаются.
   Проверить не только ширину кнопки, но и hit-area контейнера.
6. Quarter: около четверти доступной высоты, прокручивается история, поле ввода
   и переключатели не вылезают за края. Full: доступная высота visualViewport,
   safe-area и клавиатура телефона, остальные элементы не получают фокус.
7. Упорядочить CSS режима/темы: тёмная тема меняет фон открытого чата, но не
   возвращает фон hidden-контейнеру. Использовать переменные темы/явные селекторы,
   не наращивать случайные z-index и !important поверх старых конфликтов.
8. Зафиксировать понятные уровни: карта → HUD → карточки → модальные окна.
   Повышение z-index карточки само по себе недостаточно: геометрия/фокус/пустые
   области и прерывание чата должны быть согласованы.
9. Карточка здания на телефоне занимает только нужную высоту в допустимом
   максимуме; длинное содержимое прокручивается внутри. Заголовок/закрытие
   не исчезают под чатом. Прежнюю большую область «Улучшить/Снести» не считать
   историей чата: это другое окно, которое надо правильно расположить.

**Готово, когда:** выбранное здание узнаваемо при выключенных общих подписях;
его название/крестик/действия видны, все три режима чата работают, карта
принимает тапы вне видимых кнопок и окон в обеих темах.

**Готово, когда:** у маленького склада, хижины, длинного дома, высокого здания
и стройплощадки подпись располагается непосредственно над объектом, не плывёт
при зуме и не прыгает на закате. Не обещать полное отсутствие перекрытия всех
названий плотного города: это отдельная задача расположения подписей.

## 5. BUILD-01 — исключить бесполезную конкурирующую стройку

### 5.1. Модель и атомарность

1. Разделить понятия: CrewNeeded — минимум разных участников этапа; объём работы
   и занятые поручения — отдельные ограничения. Не делать лимит «три человека»
   из жалобы игрока.
2. Сервер определяет свободный полезный объём по ключу
   `(village, plot, stage, job)`: требуемое минус выполненное минус зарезервированное.
   Для labor дополнительно учитывать доступный по доставленным материалам объём.
3. Перед реализацией сверить жизненный цикл WorkContext, DB tracking и блокировку
   деревни: LoadContextAsync сейчас не отдаёт объёмы всех начатых работ. Дополнить
   необходимые данные без запроса по каждому гражданину.
4. Выбрать минимальное долговечное представление резерва. Можно вычислять его
   из сохранённых активных циклов, если их поля однозначно хранят обещанный объём;
   иначе добавить явные поля/запись и additive-миграцию. Не держать резерв только
   в памяти процесса. Не фиксировать окончательный вариант до сверки settlement.
5. Проверка свободного места, создание цикла/резерва и расход энергии — одна
   атомарная операция в существующей границе GameService. Сверить транзакции и
   VillageLocks; lock одного процесса не гарантирует защиту второго инстанса.
   При нескольких процессах использовать уже поддержанный механизм БД/версионирования,
   при необходимости точечную блокировку строки и повтор операции.
6. Учитывать все источники старта: прямой запрос, повтор, очередь, автопродолжение,
   восстановление после больницы. Предпросмотр/серая кнопка не являются защитой.

### 5.2. Сколько резервировать и что происходит дальше

7. Не ускорять стройку. Для каждого принятого поручения зарезервировать только
   гарантированно допустимый объём. Бонус навыка не должен украсть объём другого
   уже принятого поручения: полезный итог ограничен собственным резервом.
   Выбрать вычисление резерва по текущей формуле навыка/усталости; одинаково
   использовать его при старте и settlement. Не раздавать лишнюю славу/опыт
   за искусственно нулевой вклад.
8. Если весь объём уже занят, отклонить **до списания** энергии/материалов,
   вернуть понятную ошибку «Все нужные работы уже заняты». При частичном остатке
   принять только полезный остаток, если он допустим существующей единицей работы.
9. Завершение атомарно превращает резерв в выполненный вклад и освобождает
   остаток. Отмена освобождает его без изменения существующего правила оплаты
   отменённой работы. Повторный запрос/settlement не даёт второго вклада/награды.
10. Очередь сама по себе не держит место бессрочно. При её реальном запуске снова
    проверить остаток; отклонённое задание не расходует энергию и получает причину.
11. **Уточнение предыдущей диагностики:** при госпитализации нельзя просто
    освободить резерв, а после лечения автоматически продолжить уже оплаченную
    работу поверх занятых мест. Начальный безопасный вариант — сохранять резерв
    вместе с сохранённым циклом на паузе. Если это блокирует стадию надолго,
    переход к освобождению допускается только вместе с полным правилом возврата
    оплаченной работы/повторного допуска; это отдельное решение, не скрытая потеря.
12. Для старых незавершённых циклов без нового резерва нужна совместимость:
    не обнулять уже оплаченное. При запуске нового правила детерминированно
    учитывать старые циклы; случаи уже существующего перебора сохранять отдельно
    от нового допуска. Новые старты не увеличивают перебор. Схему завершения
    оплаченных старых циклов выбрать до миграции; не обещать возмещение без решения.
13. В DTO и JobCard показывать «осталось», «уже выполняют», «свободно», блокировать
    кнопку с короткой причиной и обновлять после событий. Сервер остаётся решающим.
    Проверить обычные здания, upgrades/снос и общие проекты по их разным путям;
    не применять локальную правку только к одной хижине и считать всё закрытым.

**Готово, когда:** несколько одновременных запросов не занимают один остаток;
отклонённые не тратят энергию; рестарт, очередь, отмена и больница не дублируют
вклад/списание; уже оплаченные старые циклы не теряются.

## 6. ENERGY-01 — исправить объяснение и проверить механику

1. Для жалобы #75 установить точное правило по исходнику: CycleTired вычисляется
   на старте как `currentEnergy < energyCost`, сохраняется для текущего цикла.
   Положительная энергия сама по себе не гарантирует нормальную работу.
2. Сверить стоимость каждого вида поручения, погоду, медицинские эффекты,
   дробную энергию, округление индикатора, прямой старт и старт из очереди.
   UI не должен показывать достаточную целую1, если реально меньше нужного1.
3. Вынести/использовать общий серверный расчёт стоимости. Если UI не получает
   эффективную цену, добавить её в текущий DTO/предпросмотр, не копировать
   формулы погоды и больничных эффектов в разные компоненты.
4. До старта коротко показывать требуемую энергию и причину замедления.
   Во время работы объяснить, что она начата уставшим; регенерация относится
   к следующему запуску. Не менять уже начатый таймер молча.
5. Исправить устаревшую русскую подсказку «без сил0 опыта» по реально действующим
   множителям выдачи/опыта; сверить остальные языки. По возможности значения
   получать из общего контракта, чтобы текст не расходился с кодом снова.
6. Если при достаточной энергии новый цикл всё же получает CycleTired — это
   воспроизводимый баг расчёта/очереди, исправить именно его. Если правило работает,
   закрыть ошибку как неясный UI, не менять баланс ради жалобы.

| Малые/высокие здания, стройка, день→ночь, зум | Подписи у крыши, без скачка/дублей/учёта ореола |
| На остаток2 одновременно идут3+ игроков | Полезные места заняты атомарно, лишний старт отклонён без оплаты |
| Навык даёт бонус, частичный остаток, переход стадии | Нет превышения чужого резерва, двойной славы/опыта/материалов |
| Отмена/очередь/офлайн/рестарт/лечение | Резерв и оплаченный цикл не теряются, новый старт проверяется заново |
| Энергия0/чуть ниже цены/ровно цена/чуть выше | Верный CycleTired и текст, регенерация не ускоряет текущий цикл |
| Старые циклы0.5.2 и уже существующий перебор | Нет сброса, двойной оплаты или молчаливой потери оплаченной работы |

В браузерных проверках использовать не только отдельный chat harness:
нужна реальная композиция GamePage + popup + тема. Расширить существующие
тесты по поведению, не создавать десятки тестов, повторяющих CSS-селекторы.
Тест конкурентного старта должен проходить через настоящую серверную границу,
а не только последовательно вызывать CheckJob в памяти.
Автоматика не заменяет визуальную проверку телефона: открыть итоговые снимки
и проверить человеческими глазами, особенно текст/пустые области/название здания.
