## Выбранный путь реализации

Нельзя добавлять апгрейды только в ProjectCatalog: проекты открывает StoryQuests,
и главный мост/звонница держит единственный active project. Новый апгрейд иначе
окажется недоступным до конца цепочки. Использовать обычную строительную очередь
и существующие роли/материалы/работу, параллельно с большим сюжетным проектом.

1. Добавить непланируемый обычной разметкой BuildingKind.FortificationUpgrade:
   BuildingCatalog запись с пустыми Stages/Buildablefalse. Определение работы
   выдаёт BuildingOperations.Definition для Operation=fortification-upgrade;
   не новый дом/склад/раса и не схема строительства на любом участке.
2. Служебный PlotId=fortifications, рабочий двор2.5,10.5 как у нынешнего частокола.
   WorldMap.Yard и клиентское место работы знают его, Footprint=null:
   не занимает земельный участок, не появляется фантомное здание у костра.
   RaidSimulation.Targets явно исключает такую служебную стройку.
3. Fortification.Level1..3, старые сохраняют level1 и прежний Damage0..100.
   Уровни: деревянный/бревенчатый/каменный; прочность через коэффициент при
   BreakWall, включая ворота. Пример100/200/350 условныхHP; Damage остаётся
   процентом, Blocks при100. Апгрейд НЕ сбрасывает Damage и не двигает стены.
   Новые river endcaps наследуют текущий уровень, не ремонтируют старые.
4. FortificationUpgrades domain rules: текущий уровень, цена/работа/доступность,
   request/preflight/begin/apply готовой площадки. Старт только с реальной стеной,
   ниже3, без другого апгрейда, с местом в общественной очереди, без объявленного
   или текущего набега. Повторная проверка при одобрении.
5. Новая ruler API upgrade-fortifications: LoadVillage, RequireRuler, загрузить
   completed projects→Fortifications.Ensure; owner начинает работу, governor
   создаёт обычную CivicOrder(PlotIdfortifications,Operationupgrade,BuildingKind
   FortificationUpgrade) для согласования. Owner только существующим approve.
   Все исходные материалы списывают обычные haul jobs; работа не выполняется
   моделью/владельцем мгновенно. Без реальных свечей/валюты.
6. BuildingOperations.Request/Approve — ранние ветки для служебного plot/kind,
   до обычного require completed building/footprint. Очередь, pending duplicate,
   дефолтный owner routing/notice/idempotency сохранить. Begin создаёт Site с
   TargetLevel current+1 и Scale/работой по числу существующих секций.
7. Пример стартовых цен до тестов: logs ~3Wood+1Plank на секцию, stone ~5Stone+
   1Wood+1Plank; работы минимум25–60 полезных циклов на весь контур. Не требовать
   новых ресурсов. Уточнить Craft/Technology gating на существующих каталогах.
8. Финал без бесплатного усиления во время войны: если волна объявилась, пока
   строили, полностью оплаченная/готовая площадка ждёт окончания всех волн.
   Не бросать исключение на каждом worker tick и не создавать обычное здание.
   BuildingOperations.Finish помечает работу завершённой без применения Level;
   FortificationUpgrades.ApplyReady при Save/окончании боя применяет готовый Site
   только когда нет pending raid, сохраняет проценты повреждений и убирает Site.
   Возможный общий hook перед BuildingNumbers.Ensure в SaveChanges — проверить
   корректность EF owned JSON и отсутствие двойной оплаты/награды.
9. DefensePanel → «Укрепления»: текущий материал/прочность/повреждения, следующий
   апгрейд/материалы/работа/причина блокировки, governor «Отправить заявку»;
   сохраняются кнопки ворот. Только меню, никаких новых постоянных HUD панелей.
   После API вернуть state через имеющийся onVillage. В заявке/Telegram понятное
   имя «Укрепления», без «Участокfortifications» и без выдуманного номера здания.
10. Ремонт остаётся конечной платной работой: проверить цену/скорость для более
    прочных стен, что 10% не чинится бесплатно и разрушенные ворота восстанавливаются
    тем же material. Геометрия входов/вода/соседние секции не обходятся по диагонали.
