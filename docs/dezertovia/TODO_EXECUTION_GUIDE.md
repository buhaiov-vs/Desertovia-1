Задача — точечно исправлять и расширять существующую игру автора. Сохранить .NET Domain/Infrastructure/Api, EF Core/PostgreSQL, React/PixiJS/Vite и SignalR. Этот документ подготовлен по просьбе владельца как инструкция, а не как утверждение реализации всех перечисленных функций.

**Выкладка остановлена решением D-058.** Только рабочие ветки, локальные проверки и GitHub. Не устанавливать игру или бота на сервер, не включать там Всевышнего, не отправлять настоящие предложения владельцу. Не создавать запрос, запускающий приватный release workflow. Для реализации брать объём из нового поручения владельца; само чтение этого плана не запускает работу над всеми восемью пунктами.

## 1. Режим и способ работы

**Решение владельца: GPT 6.1 SOL / Высокое для всех восьми пунктов.** Не переключать отдельные задачи на лёгкое или среднее рассуждение. Параметр модели выбирает пользователь в интерфейсе; запись в файле сама по себе его не меняет.

Высокую глубину использовать для проверки связей и сохранности. Не расширять из-за этого объём, не переписывать работающую архитектуру и не запускать полный набор тестов после каждого небольшого изменения.

Для каждого пункта до редактирования:

1. Проследить путь клиент → endpoint → права → domain rules → транзакция/побочные эффекты → DTO → SignalR → интерфейс.
2. Зафиксировать исходное поведение и требуемое изменение, что хранится в БД и кто является источником истины. Прочитать вызовы изменяемой функции и существующие проверки.
3. Проверить успешный путь, отказ без списания, повтор запроса, конкуренцию двух запросов, офлайн/перезапуск и совместимость старых данных. Для чисто визуальной правки не изобретать отсутствующую транзакцию или миграцию.
4. Выбрать минимальное изменение существующего механизма. Новые таблицы/поля добавлять только при реальной необходимости; влияние на enum, JSON, миграции, RU/EN и клиента учитывать вместе.
5. Закончить связанный код блока. Сразу записать короткую точку продолжения, чтобы при сжатии не потерять следующий шаг; не сохранять длинные внутренние рассуждения.
6. После завершения всего согласованного объёма провести итоговые проверки по разделу 14, затем исправить выявленные ошибки и повторить только необходимые проверки.

Режим планирования помогает согласовать новый контракт. После команды реализовать работать в обычном режиме исполнения с высоким рассуждением. Уже разрешённый пакет доводить до результата без запроса подтверждения между каждым файлом или этапом.

## 4. Обязательные ограничения

- Одна Дезертовия, без кланов. Возможности основы автора сохранять. Ограничения нашего запуска оформлять настройкой, не удалением общей инженерии.
- Сложная медленная кооперация: не ускорять добычу/стройку, не увеличивать выдачу и не обходить ограничения полезной работы. Очередь одно текущее действие плюс одно следующее.
- Нынешний прогресс, навыки, опыт, слава, имущество, жильё, браки и незавершённые оплаченные действия сохраняются. Не восстанавливать старую БД поверх нового прогресса.
- Идентичность — AccountId и числовой Telegram ID; ник — отображаемое имя.
- Общие ресурсы внутри царства. Внешняя частная стройка не получает общий запас. Помощники готовят заявки; окончательное решение царя.
- Реальные свечи батюшки и донаты отделены от тестовой экономики. Дуэльное лечение использует существующие правила бота, без второго списания.
- Всевышний один. Только сервер назначает допустимые действия и применяет последствия. Чат, промпт и модель не предоставляют права на деньги или администрирование.
- Новый художественный проект не запускать. Использовать существующие проверенные спрайты. Не выдавать картинку замка за готовую механику.
- Секреты, .env, сырые отзывы, рабочие cookie, снимки профилей и резервные копии не публиковать. Не обращаться к продакшену ради локального теста.
- Различать PLAN, BRANCH, VERIFIED и LIVE. В патчноут не записывать несуществующую функцию.

4. Старые остатки обозначить начальным снимком на дату запуска учёта. Не придумывать их историю, автора добычи или себестоимость. Журнал материалов не выдавать за полный бухгалтерский ledger денег.
5. Сервер даёт фильтры и пагинацию. Игрок видит понятное «Камень −4 · ремонт мастерской», а не технические JSON и AccountId. Права просмотра учитывать отдельно.
6. Всевышнему передавать ограниченные агрегаты за период: приток/расход/причины/дефицит, с явной границей начала учёта. Экономические правила и итоговые суммы считать обычным кодом.

**Приёмка:** фактическая дельта запасов объясняется операциями, откат не оставляет ложной записи, повтор не удваивает журнал, производство имеет затраты и выпуск. UI не загружает всю историю разом.

## 11. Пункт 6 Инвентарь и экипировка

**Файлы:** существующие `web/src/ui/{InventoryPanel.tsx,HandsCard.tsx,StorageCard.tsx,CharacterSheet.tsx}`, `web/src/api.ts`, `src/Desertod.Domain/{Combat/ArmoryCatalog.cs,Combat/CombatRules.cs,Entities/Citizen.cs}`, соответствующие DTO и серверные операции.

1. Сначала привести отображение в порядок: ноша игрока, общий склад, временно выданная боевая экипировка и личное имущество должны быть явно различимы. Показать вместимость, предметы и действительные боевые параметры.
2. Нынешнее автоматическое вооружение/возврат на склад сохранять, пока нет явного решения изменить его. Не выдавать автоматически полученное оружие за личную собственность.
3. Личную экипировку добавлять только с моделью владельца и состояния: на складе/выдано/надето/в лоте/передано. Один предмет не может одновременно участвовать в двух несовместимых состояниях.
4. Передача проверяет принадлежность, доступность предмета, вместимость получателя и действующие ограничения лечения/боя. Применять атомарно с уникальным ID операции. Повтор, два параллельных получателя и обрыв соединения не дублируют предметы.
5. Общую вещь нельзя продать от собственного имени. Материал общего склада можно перепродать после разрешённой покупки за игровую валюту с переходом собственности — это зависимость от пункта 8.

**Приёмка:** существующий инвентарь улучшен, второй интерфейс не создан; общая и личная собственность понятны; временная экипировка корректно возвращается; при передаче никто не теряет и не удваивает предмет.

## 12. Пункт 7 Компактный мобильный интерфейс и чат

**Файлы:** `web/src/ui/{ChatPanel.tsx,SettingsPanel.tsx,NotificationToggle.tsx,GameMenu.tsx}`, `web/src/pages/GamePage.tsx`, `web/src/notifications.ts`, стили и RU/EN.

1. Независимо настроить игровые всплывающие сообщения. Не смешивать переключатель с системным Web Push. Выключение всплывашек сохраняет историю и счётчик непрочитанных.
2. Упоминания выбирать из доступного списка игроков; ID адресата стабильный, ник только отображается. Не создавать обязательную Telegram-рассылку и не вставлять пользовательский HTML.
3. Энергию/еду показывать компактно, без новой полноширинной нижней полосы. Карта остаётся основной частью экрана; выбранная карточка, чат и модальные окна не перекрывают друг друга.
4. Если добавляется «Повторить», это одно обычное действие с серверным допуском и очередью 1+1. Никаких бесконечных циклов, скрытой третьей очереди или обхода исчерпанного участка.
5. Не терять черновик чата, прокрутку и набранное количество на складе из-за фоновых обновлений. Настройки сохранять совместимо с прежними пользовательскими предпочтениями.

**Приёмка:** ширины 320/390/430 и ПК 16:9; светлая/тёмная тема; чат скрыт/четверть/полный; открытая клавиатура; длинные имена; выбранное здание; непрочитанные сохранены. Эмуляция Chromium не равна проверке физического Safari/старого Android — в отчёте указать фактическую среду.

## 13. Пункт 8 Дезкоины рынок обмен и налоги

**Режим: высокое рассуждение. Зависимости: журнал операций, принадлежность имущества и атомарные операции.**

1. ДЗК — отдельная игровая валюта. Сначала проверить существующие модели; ресурс Gold, реальные свечи и тестовые свечи — разные сущности. Не превращать добытую золотую руду в деньги автоматически.
2. Зафиксировать единицы, источник выпуска, полезные оплачиваемые действия, траты, возвраты и права казны. Старые примеры ×10, зарплат, курса и налоговой шкалы из legacy Python не переносить вслепую в C#.
3. Использовать целые минимальные единицы валюты, проверку границ и детерминированное округление. Кошельки и ledger меняются атомарно; операции имеют уникальные ключи. Для нескольких кошельков единый порядок блокировок и повтор транзакции без второго платежа.
4. Полезный оплаченный труд подтверждается серверным завершением, не клиентским кликом. Отдых, отмена, повтор запроса и бесполезный вклад не печатают валюту. Источник и получатель каждой выплаты видны в учёте.
5. Рынок: лот резервирует предмет/материал, цену и продавца; покупка проверяет остаток, деньги и вместимость. Покупка/отмена/возврат при гонке завершаются единожды. Для перепродажи общего материала сначала отдельная покупка у царства с передачей собственности.
6. Обмен пока только на **тестовые** свечи. Конкретный курс, дневной лимит и общий фонд закрепить в конфигурации согласно новому решению владельца; старые примеры не считать согласованными. Лимит действует на аккаунт, не на ник/устройство. Граница суток хранится явно, отображается время сброса.
7. Будущий настоящий обмен должен разделять общий лимит 20 свечей за все игры через authoritative сервис бота. В этом этапе настоящий обмен не включать и донатные свечи не пересчитывать.
8. Налог прогрессивный: необлагаемый минимум, повышенная ставка только на превышение. Не облагать возврат, внутренний перенос, исходный баланс или обмен как новый трудовой доход. Для налога на торговую прибыль нужна известная себестоимость; если её нет, не выдавать оборот за прибыль.
9. Пока шкала/фонд/доли не выбраны, подготовить конкретный расчёт для рассмотрения и preview, сохранив автоматические списания выключенными. Налог в казну перераспределяет деньги; только явно выведенная часть уменьшает денежную массу.
10. Всевышний получает агрегаты, объясняет дисбаланс и предлагает ограниченное изменение. Модель не исполняет произвольные суммы/SQL и не меняет курс, налог или кошельки текстом ответа. Повышение прав требует отдельного явного решения владельца.

**Приёмка:** баланс денег объясняется выпуском, переносами и выводом; двойной клик не печатает/не списывает дважды; гонка лота даёт одного покупателя; отрицательный баланс/сумма, переполнение, подмена владельца и повтор exchange исключены. Реальные аккаунтные свечи не меняются.

## 14. Проверки после завершения выбранного объёма

Сначала закончить связанный код и миграции выбранного пакета, затем проверить его целиком. Не прогонять полный набор после каждой надписи. После найденной ошибки — прицельный повтор; полный CI на окончательном исполняемом источнике. Чужой или старый зелёный SHA не подтверждает новые изменения.

| Область | Достаточная значимая проверка |
| --- | --- |
| Запрет разрушения | Single-world HTTP + сервисный путь; сравнение исходного/конечного прогресса; legacy multi-world; logout не затронут |
| Директор и рейды | Реальная PostgreSQL запись/загрузка маршрута, свежие условия, повтор согласия, поздняя модель, чужой ID, Off и таймер волн |
| Миграции | Старая локальная схема с реальными формами JSON → новая; сохранены профили/XP/вещи/начатые циклы и legacy overflow |
| Замок | Единственность при конкуренции, роль царя, стадии/апгрейд, запрещённые участки, старые здания и берег |
| Журнал | Commit/rollback/retry, правильный итог дельт и разграничение прав |
| Деньги и торговля | Двойные запросы, две покупки одного лота, точная сумма/лимит/сутки/округление, возврат и отсутствие реального платежа |
| UI | Существующие Playwright сценарии плюс только недостающие реальные регрессии; телефон/ПК/темы/клавиатура/переподключение |

В текущем окружении dotnet находится в `/workspace/dotnet`; если он не в PATH, настроить DOTNET_ROOT/PATH. Перед использованием Docker прочитать инструкции среды и проверить локальный daemon. API tests сами создают PostgreSQL через Testcontainers. Не использовать строку соединения production.

Примеры команд из корня игры:

```bash
dotnet build Desertod.slnx -c Release
dotnet test tests/Desertod.Api.Tests --filter 'FullyQualifiedName~LeavingVillageTests|FullyQualifiedName~SingleWorldLaunchTests'
dotnet test tests/Desertod.Api.Tests --filter 'FullyQualifiedName~AlmightyApiTests'
```

Из `web`: `npm run lint`, `npm run build`, затем выбранные существующие `npx playwright test` сценарии. Полный `dotnet test Desertod.slnx -c Release` и обязательный repository CI — один раз на законченный пакет. Если бот не менялся, не повторять его полный suite. Если менялся, целевые director/proxy/hospital проверки и его финальный CI обязательны.

Для браузерных тестов использовать отдельную локальную БД; в текущей среде она могла работать на порту 55439, проверить фактический порт перед запуском. Не собирать Vite в wwwroot одновременно с .NET build из-за гонки static assets. Не ослаблять assertions/авторизацию ради зелёного результата. Не добавлять тысячи однотипных тестов для текста.
