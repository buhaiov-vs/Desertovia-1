# Всевышний — подробный план имплементации

D-055 ·15.10.2026 · **PLAN, реализация директора не начата**.
Требование владельца: один ИИ, общие память/личность/замысел; бухгалтерия,
командование врагами, сложность, ивенты и общение — обязанности этого директора.
Общий замысел: [ALMIGHTY_DIRECTOR_PLAN.md](ALMIGHTY_DIRECTOR_PLAN.md), тактика:
[BATTLE_PLAN.md](BATTLE_PLAN.md). Этот файл — технический порядок реализации,
сохраняемый после сжатия контекста. Не разрешение выкладки или автокоррекции денег.

## 0. Контракт и результат

Создать один управляющий контур: **наблюдать → вспомнить замысел → выбрать
допустимое действие → проверить → применить → запомнить результат**.

- Сохранять .NET Domain/Infrastructure/Api, EF/PostgreSQL, React/Pixi/SignalR.
- Один DirectorService/контур решений на мир, не несколько автономных агентов.
- Код считает экономику, исполняет бой/маршруты/таймеры, валидирует права. Это
  инструменты одного ИИ. Модель не получает SQL/shell/прямую запись в базу.
- Перезапуск, две API-копии и повтор запроса не дублируют событие/награду/урон.
- Сохранить медленную работу, queue1+1, энергию, регенерацию ресурсов, госпитальные
  ограничения, одобрение царём строек/расселения и настоящие свечи отдельно.
- Экономическая обязанность сначала только отчёт/совет, без налоговых списаний,
  изменения курса или принудительного исправления кошельков.
- Пока составляем план. Runtime остаётся прежним; кандидат PR33 содержит
  патчноуты и исправления D-053, а не работающего Всевышнего.

Режимы одного и того же кода: `Off → Observe → Propose → LimitedAuto`.
Переключение выполняет только владелец, с версией policy и журналом. Сразу писать
контракт для всех режимов, но поэтапное включение не означает переписывать систему.

## 3. Сохранённые данные и память

### 3.1 DirectorState — одна запись на VillageId

Mode, StateVersion, PolicyVersion, CurrentIntent, Phase, IntentExpiresAt,
LastDecisionAt, NextReviewAt, RecoveryUntil, ChatCursor, NeedsReview,
LeaseOwner/LeaseUntil, KillSwitch, UpdatedAt. Уникальность VillageId.
Phase: спокойно/подготовка/напряжение/событие/восстановление; это состояние
директора, не замена исхода Raid. CurrentIntent — ограниченный по длине замысел.

### 3.2 DirectorSnapshot — проверяемые факты

SnapshotId, VillageId, CapturedAt, SchemaVersion, Fingerprint, агрегаты,
known/unknown/missing признаки и ссылки на события-основания. Не обещать
встроенную общую WorldRevision: для свежести сравнивать DirectorStateVersion,
срок сводки и повторно читать критические факты внутри lock. Fingerprint —
для дедупликации, не замена повторной проверки прав/охраны/угрозы.

### 3.3 DirectorProposal / DirectorDecision

Id, WorldId, SnapshotId, StateVersion, PolicyVersion, ModeAtCreation,
AllowedOptionId, ParamsSchemaVersion, ReasonCode, EvidenceIds, ShortExplanation,
ExpiresAt, Status, DecidedByAccountId, AppliedWorldEventId, CreatedAt.
Статусы: Draft → PendingApproval → Approved → Applied; альтернативы
Rejected / Expired / Superseded / Failed. Approved ещё не означает Applied.
Повтор approve возвращает ту же запись/результат, а не новый event.

### 3.4 WorldEvent / Raid linkage

EventId, WorldId, Kind, CatalogVersion, Source(manual/director/night),
ProposalId?, Phase, ScheduledAt, AnnouncedAt, StartsAt, EndsAt?, Outcome,
CancelledReason?, BudgetCost. Хранить ссылки на конкретные Raid IDs/волны;
не копировать их HP/лут/раны во второй независимый расчёт.
Уникальный ProposalId на событие, уникальные ключи применения эффектов.

### 3.5 Memory и бухгалтерия

DirectorMemoryFact: факт/источник/время/актуальность/видимость/срок, а не только
литературное резюме. Замысел и последние исходы сохраняются отдельно от чата.
Резюме модели не может изменить факт «бой проигран» на «победили».
Хранить ограниченный набор актуальных фактов + журнал событий с пагинацией;
старую историю сворачивать, не обрезая ещё действующие обязательства/таймеры.

EconomyObservation — баланс/склады на время снимка. Полезен без ledger,
но разница снимков не называется прибылью/полным оборотом.
EconomyEntry — отдельный будущий точный журнал операций с operationId,
resource/currency, amount, source/destination, reason, occurredAt, knownCost.
Материалы и валюты не смешивать, стоимость неизвестна → unknown.
События изготовления/перекладки/возврата не считать повторной эмиссией.

### 3.6 Надёжность и приватность

DecisionLog, ModelCallRecord (model/version, tokens/cost/status/latency без
ключей), ModelBudget, Outbox, ChatTriggerWindow. Уникальные ключи дедупликации,
индексы VillageId+Status+DueAt, retention/лимит размера.
Additive EF migration. Новые миры/старые записи получают Mode=Off;
существующие профили, деньги, XP, профессии и сроки не переписывать.
Все timestamps UTC, пользовательский интерфейс явно называет шкалу времени.

## 5. Единый цикл и контракт модели

### 5.1 Порядок одного решения

1. В короткой транзакции забрать due world через persisted lease и зафиксировать
   decision job/state version. Отпустить DB lock.
2. Собрать snapshot, замысел, релевантную память и допустимые варианты.
3. Зарезервировать квоту вызова; проверить timeout/общий token/cost limit.
4. Один DirectorModelClient вызывает одну личность Всевышнего. Не запускать
   параллельно автономных экономиста/командира/сценариста.
5. Строго разобрать ограниченный JSON: snapshotId, expectedStateVersion,
   intentUpdate?, selectedOptionId|null, reasonCode, evidenceIds, reviewAfter,
   proposedSpeech?. В первом срезе максимум одно действие на decision.
6. В коротком существующем world lock проверить lease/job, mode/kill switch,
   версию policy/state, срок предложения, свежие условия/общие бюджеты.
7. Observe — записать решение; Propose — сохранить карточку царю;
   LimitedAuto — применить только разрешённый whitelist.
8. В одной транзакции состояние/расход бюджета/связь event/proposal/outbox.
9. Доставить подтверждённое уведомление. Запланировать следующий обзор.

LLM не вызывается внутри world lock. За время вызова начался ручной бой —
предложение пересматривается/отклоняется, не добавляет второй бой.
Два worker не могут применить одну job: lease + compare-and-swap + уникальные
ключи. После рестарта подхватить сохранённые jobs, не назначить пачку пропущенных
опасностей. Принятый ответ сохраняется; повтор HTTP не означает повтор решения.

### 5.2 Модель, транспорт и расходы

Конкретную модель выбрать после проверки структурированного вывода, задержки,
стоимости и доступности наших провайдеров. Не печатать/не сохранять ключи в git.
Один model client/инструкция/память на мир. Резервный провайдер при необходимости
исполняет ту же личность, без второго независимого замысла; разрешённый retry
ограничен. Ошибка не запускает случайное событие.

Существующий speak не контракт JSON-управления. Для private bridge при выборе
этого пути спроектировать отдельное director-action с request size/time limits,
подписью, без auth/hospital инструментов. Изменение игры и бота согласовать
по версии протокола; раньше готовности bridge функциональность Off. Можно
отдельный серверный transport с тем же secret storage — выбор после аудита,
без добавления ключей в браузер и без изменения auth-контракта.

Общий учёт стоимости всех обязанностей. Кандидат: стратегический вызов не чаще
раза в15мин, максимум4/час на мир; NPC-ответы имеют свою очередь приоритетов,
но тот же общий денежный бюджет. Не считать, что4 вызова включают неограниченный
чат. Жёсткие пределы input/output, число retries и дневной cap обязательны;
стоимость неизвестна — консервативный резерв. При исчерпании квоты обычная игра
продолжается, модельный автомат не увеличивает частоту вызовов.

Параметры варианта определяет EventCatalog, не модель: enemy/size/waves,

инвалидируют конфликтующие предложения. LimitedAuto заменяет только конкретно
покрытое планирование; Off возвращает прежнее, без повторного решения за уже
учтённую ночь/дублирования scheduled wave. Тестировать переход каждого режима.

Нельзя вызвать защищённый CallUndeadAsync с подставленным accountId царя:
вынести общий внутренний запуск в доверенный executor с собственной policy.
Пользовательский API сохраняет проверку OwnerAccountId. Любое изменение
расписания и ledger события — внутри того же world lock.

Кандидаты баланса: одна авто-опасность одновременно,60мин между событиями,
после тяжёлого поражения120мин + проверка боеготовности. Предупреждение не короче
действующего. Числа подтвердить симуляцией, не утверждать этим документом.
Не применять авто-нападение без пригодной охраны, не охотиться на офлайн/новичков.
Богатство само по себе не повод усиления. Не менять ресурсные притоки/скорость
работ. Разрушение в ноль, катаклизмы и реальные финансовые операции вне первого среза.

## 7. Чат и батюшка — тот же директор

Обработчик чата создаёт повод в общей очереди, а не второго самостоятельного ИИ.
Direct mention приоритетнее фонового обзора, но не обходит квоты/антифлуд.
Для короткого ответа отправляется разговорный view контекста того же директора;
скрытые планы врага/личные данные в реплику не попадают. Обычный ответ не обязан
менять общий замысел. Устаревший фоновой intentUpdate не затирает более свежий.

Чат «скучно/готовы/все построили/нужна помощь» → нормализованный ChatTrigger
с evidence IDs, distinct authors, окном, cooldown. Несколько разных участников
(кандидат3 за10мин) + факт мира. Спам одним человеком не увеличивает бюджет.
Это условие не относится к личному обращению к батюшке.
Жалоба о баге → owner report, не карательная сложность. Донаты/оскорбления
не меняют допустимость атаки или лечения.

Фразы игроков и резюме из них остаются недоверенными данными. Evidence ID
должен существовать в разрешённом snapshot. Model-provided role/owner flag игнорируется.
Обрезать длину/удалять управляющие символы; вывод текстом, не HTML/команды.

Сохранить ChaplainChatWorker как механизм доставки/антифлуда. Когда новый контур
включён, старый путь генерации для этого мира не работает одновременно.
На Off вернуть прежнее поведение; одинаковое событие не озвучивать дважды.
Существующие лимиты NPC входят в общий бюджет, фоновые реплики при тишине запрещены.
Публикация после commit; failed/outdated предложение не становится слухом о
«точно назначенной атаке». Сообщения в Telegram этим не разрешаются.

## 8. Бухгалтерия и новые мирные события

Первый отчёт: баланс запасов, производственные возможности, износ/ремонт,
потребности стройки, невыполненные работы и достоверность данных. До ledger
нет выдуманного точного дохода профессии и автоналога.

Инвентаризация денежных и материальных операций: добыча, производство,
доставка/перекладка, потребление, зарплата, рынок/комиссия, exchange/налог preview,
ремонт/стройка, лечебные оплаты. Существующие реальные сервисы оплаты остаются
единственным владельцем соответствующего баланса. Новые события ledger писать
рядом с фактическим commit операции, с operationId и идемпотентностью; старые
события не восстанавливать фиктивно как достоверную историю.

После наблюдения — рекомендации царю: дефицит работ для профессии, устойчивый
излишек/недостаток, возможный диапазон цены/расходов с основанием. Всевышний не
получает инструмента автоматически списывать налог/свечи.

Караван/ярмарка/общий заказ — отдельные сценарии после базового директора.
Для каждого: источник товаров/денег, конечный запас, цена/эмиссия/расход,
допуск, длительность, участие, выполнение, награда, отмена/повтор, UI/уведомление.
Без этих правил нельзя дать модели «придумать и выполнить» новый ивент.
Отсутствие ресурсов не лечится созданием материала из воздуха.

## 9. Военачальник врагов — тот же интеллект, следующий технический срез

1. Ввести серверную проходимость/направления, правила реки/закрытого моста,
   достижимые цели и связь существующей общей обороны с участками.
2. CommanderKnowledge — последние разведданные/время/уверенность. Из глобального
   контекста директора нельзя выбрать неизвестную или запрещённую цель:
   сервер выдаёт допустимые варианты и проверяет их фактическое исполнение.
3. Начать одним отрядом/подходом. Приказ: цель/направление, срок, версия,
   условие смены/отступления. Прибытие охраны/преграда реально меняет исход.
4. Тот же Всевышний выбирает стратегию/допустимый приказ при значимых изменениях;
   код по тикам ведёт движение/дистанции/урон. Нет сетевого LLM на каждый удар.
5. Локальный детерминированный fallback исполняет последний валидный приказ
   или разрешённое отступление, не получает новых солдат при сбое.
6. Сохранить ранения/переноску/больницу, награды и максимальный бюджет события.
   Потом несколько отрядов/перегруппировка/стены/башни по BATTLE_PLAN.

SignalR передаёт состояние/приказы/опорные точки; Pixi анимирует, не решает исход.
Показ волн по strikesAt из D-053 не откатывать. Этап требует полноценной проверки
баланса, не выдавать его за настройку существующей анимации.

## 10. Панель царя, API и права

Вкладка «Город» → кнопка «Всевышний». Телефон: новый экран внутри меню с возвратом,
карта/чат не получают постоянную широкую полосу. ПК та же логика в существующем
окне. RU/EN, светлая/тёмная тема,320px/длинные тексты/пустые и error states.

Экраны: режим/статус, текущий замысел/последний анализ, предложения, экономика,
журнал, лимиты. Карточка: что/почему/масштаб/последствия/предупреждение,
источники фактов, срок актуальности, Одобрить/Отклонить. Текст модели не
обязательный длинный абзац: показатели и короткие причины.

Предлагаемые endpoints под /api/villages/{slug}/director:
- GET state, proposals, decisions (cursor), economy — только owner;
- PUT mode/config — owner, expectedStateVersion, только разрешённые настройки;
- POST proposals/{id}/approve|reject — owner, requestId, expectedVersion;
- POST pause — owner, останавливает новые назначения;
- отмена уже объявленного события — отдельное явное действие по его правилам.

Идентичность по серверной AccountId/Telegram linkage, не по нику.
Помощники пока не получают права менять режим/окончательно утверждать.
Клиентский disabled не защита: API проверяет каждое действие. Обычный житель
видит только уже объявленные события/правила, не чужие отчёты и скрытые планы.
Старые endpoints игры сохраняются. События UI только новые DTO, без утечки
snapshot чата/секретов в общий VillageState/SignalR.

## 11. Реализация одним согласованным пакетом

| Шаг | Работа | Готовность перед итоговыми проверками |
| --- | --- | --- |
| 0 | Аудит источников/ledger/bridge и измерение нынешнего боя/цикла | Таблица достоверных метрик, нет обещаний отсутствующих функций |
| 1 | Domain contracts, policy/catalog, состояния/инварианты | Все режимы типизированы, off по умолчанию |
| 2 | EF migration/state/memory/jobs/log/budget/outbox | Durable IDs, уникальные ключи/индексы, old data не затронуты |
| 3 | Snapshot/наблюдения/допустимые действия | Факты/unknown/свежесть, закрытые данные отделены |
| 4 | Единый DirectorService и fake/model transport | Lease, лимиты, structured output, LLM вне lock |
| 5 | Proposal/apply/общий raid scheduler | Approval/idempotency, старые сроки боя, manual/night/auto согласованы |
| 6 | Общая память/очередь чата/батюшки, read-only экономика | Нет второго принимающего решения ИИ и двойной генерации |
| 7 | Owner API/панель/журнал/метрики/kill switch | Телефон/ПК, права/ошибки/ретраи, без overlay поверх карты |
| 8 | Финальные проверки всего среза, исправления, CI | Критерии ниже; не бесконечные полные прогоны после каждой кнопки |
| 9 | Отдельно геометрия/приказы/боевой вертикальный срез | Реальная тактика, а не новая формулировка общей Defense |
| 10 | Отдельно новые сценарии жизни и их экономика | Определённые правила/расходы, каталог расширяется без нового директора |

Первый полноценный пакет — шаги0–8: наблюдение, память, предложения существующих
событий, речь/фактический экономический отчёт и панель. Ограниченный автомат
подготовлен, но активация отдельно после наблюдения. Самостоятельные налоги,
катаклизмы/разрушение в ноль и полный командир не включаются случайно этим пакетом.

В процессе написать необходимые проверки рядом с модулями, затем закончить весь
согласованный код и выполнить общий поиск ошибок/проверки. Повторять полный
набор только после существенных исправлений/нерешённых рисков. Обязательный CI
не отключать; точечные проверки для исправленного сбоя допустимы.

## 12. Матрица финальной проверки

- Domain: фиксированные время/seed/snapshot, none/неизвестные варианты,
  prerequisites/пределы/предупреждения/передышки/разрешённые последствия.
- API/DB: owner vs citizen/governor/аноним; повтор approve; два API/worker;
  lease истёк/ответ опоздал; manual бой между snapshot/apply; смена режима;
  падение до/после commit, outbox retry, миграция существующих данных.
- Модель fake: timeout/429/5xx/невалидный JSON/неизвестный инструмент/огромный
  ответ/выдуманный evidence ID/исчерпание бюджета/смена provider. Игра не зависает.
- Чат: direct mention, молчание, спам одного, общий лимит/дедуп, смена вкладок,
  prompt injection/поддельный царь; отсутствие скрытого плана в публичной речи.
- Экономика: повтор доставки не эмиссия; unknown остаётся unknown; ledger суммы
  сходятся с реальными commit; рекомендации не меняют баланс/курс/налог.
- Мир: пусто/один новичок/все ранены/офлайн/полный склад без охраны; тяжёлое
  поражение; ночная+ручная+директорская волна; перезапуск/простой, без догоняющей
  пачки нападений. Pending бои продолжаются при выключении модели.
- UI:320px/ПК, обе темы/языка, долгий текст/клавиатура, pending/error/retry,
  stale карточка/двойной тап, история/патчноуты, отсутствие перекрытий чата.
- Тактика этапа9: река/мост/закрытый проход/недостижимая цель, изменение
  укрепления/позиции охраны, недопустимая разведке цель, reconnect/однократный лут.
- Сохранность: identities/XP/skills/renown, деньги/материалы, ранения/работы и
  оплаченные циклы до/после не теряются. Нет реальных тестовых платежей/сообщений.

Модельный текст не тестировать на точную литературную фразу. Проверять инструменты,
права, факты, бюджеты и последствия. Сначала симуляция без внешней модели;
интеграционный лимитированный реальный вызов — только в разрешённой среде,
без исходных ключей/сырого чата в отчётах.

## 13. Включение, наблюдение и откат

После отдельного поручения на выпуск: подтвердить точный source/CI, свежий
backup, миграции и baseline сохранности. Новый код стартует Off, проверяются
health/auth/bridge/обычная игра/отсутствие самопроизвольных событий.
Далее Observe: сравнить решения с действительной жизнью, расход/ошибки,
неизвестные показатели и устойчивость памяти. Затем Propose с ручным одобрением.
LimitedAuto — отдельное включение только whitelist после реального наблюдения;
период/пороги выбрать по данным, не объявлять «обучился сам» после пары ответов.

Наблюдаем: частота/размер событий, прорывы/потери, время восстановления,
отклонения/просрочки, модельные расходы/latency, queue depth, двойные применения,
доставка уведомлений, полезность рекомендаций/достоверность экономики, флуд.
Kill switch запрещает новые автодействия; pending предложения перестают
применяться. Назначенные бои/таймеры/оплаты не исчезают. Совместимый rollback
кода без отката живой БД назад; порядок при новой миграции проверить заранее.

При выпуске номер package.json/lock + запись в patchNotes.ts + release record
обновляются вместе. В патчноуте различать «предложения Всевышнего» и включённый
автомат, не обещать ещё отсутствующую тактику/караваны. Сейчас номер не менять.
