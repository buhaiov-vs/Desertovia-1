# D-073: заявки посадников через батюшку, выпуск0.7.1

16.10.2026 владелец явно разрешил исправление и установку0.7.1 сейчас.
Это отменяет прежний repository-only hold D-071/D-072 для данного пакета.
Версия остаётся0.7.1, включает проверенный PR44 и парную идентификацию отзывов.

Причина: новый путь BuildingOperations.RequestBuild сохранял CivicOrder,
но не связывался с Telegram. Уведомления Всевышнего — отдельный механизм.
Теперь отдельный worker каждые15с берёт одну pending-заявку build/upgrade/demolish
основной деревни, включая старые. Режим/бюджет ИИ не влияют на доставку.
Только Telegram-привязка владельца + bot OWNER_IDS, не ник. Личка царя:
автор, вид здания, операция, координаты, одобрить/отклонить.
Housing не входит в эту очередь. В игре заявки и права остаются прежними.

Очередь в прежнем JSON CivicOrders: NoticeState/NoticeAt, совместимая backfill
миграция без удаления заявок/ресурсов. Claim под общей транзакцией/блокировкой,
сеть вне неё. Бот сохраняет квитанцию по UUID заявки до send_message.
Sent/Unknown не пересылаются вслепую; однозначный отказ Telegram или недоступный
bridge допускает повтор через5мин. Зависший game Sending повторно сверяется
с той же bot-квитанцией через2мин, не создаёт новый ID/дубликат.

Кнопки только в личке OWNER_IDS; подписанный bridge /api/civic/vote дополнительно
сверяет Telegram ExternalLogin настоящего владельца и PrimaryVillage.
Полная штатная проверка BuildingOperations.Approve при согласии; повтор/ответ
после решения из игры не начинает вторую стройку и не отменяет первое решение.
Материалы, навыки, деньги, здания автоматически не выдаются и не сбрасываются.

Новый выпуск требует новых exact CI/payload/operator/manifest, PostgreSQL/SQLite/
config backups, отдельной проверки сохранности. Старый rollout0.7 не повторять.
Проверки и фактические runIDs дописываются после выполнения, подготовка не deployment.
